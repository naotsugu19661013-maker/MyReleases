# Software Upstream Documents

ソフトウェア開発文書を、その文書が決定・記録する事項とプロジェクトの正本関係に従って作成・改訂・レビューする。共通品質を中核とし、基本設計書だけに専用の記述範囲・粒度ルールを適用する。その他の開発文書は固定の種別プロファイルを設けず、依頼の目的と文書固有の責任から内容を決める。

## 適用範囲と正本確認

基本設計書を含む開発文書の新規作成、改訂、レビューに使う。詳細設計、調査記録、作業計画、検証記録なども、依頼された文書が所有する内容を扱う。文書作業の依頼だけを根拠に、実装・試験の実行や後続工程へ進まない。

着手時に、適用される `AGENTS.md`、文書管理規定、文書一覧・正本案内、現行の承認済み資料を確認する。次の事項を依頼と照合する。

- 対象文書の目的、読者、今回決定・記録する事項、対象範囲。
- 参照する正本とその版・承認状態、他文書との所有関係。
- 作成・改訂・レビューの別、変更可能な箇所、保存先、終了条件。

正本の優先順位はプロジェクトの規定に従う。基本設計書の存在を前提にせず、別の文書が正本ならその関係を尊重する。文書名や内容から推測した位置付けを正式な権限とみなさない。位置付けや正本が衝突するときは、確認できる範囲で作業し、解消できない問題を報告する。推測した責任範囲を根拠に内容を削除・移動しない。

すべての対象文書で [共通品質ルール](references/common-quality.md) を読む。基本設計書には、さらに [基本設計の記述範囲と粒度](references/basic-design.md) を適用する。複数の役割を持つ文書は、各部分が所有する事項を区別し、他文書の役割を機械的に取り込まない。

既存の命名・版・承認・変更履歴・索引・保管規定に従う。規定の不足を理由に新しい管理文書や管理体系を作らず、対象外の管理問題は別途報告する。

## 作業の流れ

1. **意味と権限を整理する。** 正本、現行文書、変更指示、レビュー、調査結果から、今回扱う意味とその根拠・状態・所有先を把握する。資料の段落や旧章番号をそのまま転記先に割り当てない。
2. **所有内容と読む順序を決める。** 今回の文書に必要な判断・記録を抽出し、他の正本に属する仕様は必要な参照にする。章立ては目的、実際の内容、既存の正本構造、管理規定から選び、項目数や共通テンプレートを強制しない。
3. **依頼された操作を行う。** 新規作成では、根拠のある内容を組み立て、未決定・未確認事項を分ける。改訂では、旧文書の有効な意味を把握してから、指定範囲の表現・構造・変更差分を反映する。改訂時の意味保持は共通品質ルールに従う。
4. **品質ゲートを確認する。** 出力を先頭から末尾まで読み、次節の観点を一度に確認する。欠陥を修正した場合は、その箇所と影響する関係を再確認する。

レビュー・監査だけの依頼では読み取り専用とする。対象文書、メタデータ、関連文書を編集せず、修正文書やパッチも作成しない。指摘には位置と根拠、利用・判断への影響を付け、観察事実と解釈、利用を妨げる問題と改善事項を区別する。比較資料がない場合は、過去の内容保持を判定できないことを明記する。

## 品質ゲート

新規作成・改訂では完成物に、レビューでは指摘と評価に、次の観点を適用する。

- 文書の目的と記載内容が一致し、必要な判断・記録がその文書の責任範囲で成立しているか。
- 正本の仕様を重複・再定義せず、各事項の所有先と参照先が明確か。
- 承認済み判断、必要な制約・条件・例外を維持し、根拠のない仕様追加や廃止事項の復活がないか。改訂では旧文書との意味の対応も確認する。
- 主語・述語、条件・結果、因果・対比・原則と例外、用語・指示語が自然につながり、読み上げ順序で理解できるか。共通品質ルールの表現制限にも適合しているか。
- 文書全体に重複説明、不要な背景・具体例・作業経緯が残らず、必要十分な構成になっているか。
- 基本設計書では、基本設計として必要な判断が成立し、後工程で決められる詳細を過剰に固定していないか。

参照先と必要な節へのリンク、適用される管理情報も確認する。構文検査や文字数だけで意味・文章品質の合格を判定しない。解消できない欠陥、必要な判断の不足、形式の衝突があれば、対象と理由を示し、完成・承認可能とは報告しない。

完了報告には、扱った文書の目的と正本、主な変更、意味保持と品質確認の結果、未決定・確認待ち事項とその影響を簡潔に示す。新たな未解決事項がなければ、その旨を明記する。草案、レビュー済み、承認済み、実装済み、検証済みの状態は区別し、与えられていない承認や実施していない検証を主張しない。
